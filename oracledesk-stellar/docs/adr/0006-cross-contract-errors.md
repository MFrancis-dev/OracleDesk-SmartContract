# ADR 0006: Canonical cross-contract error propagation

## Status

Accepted (issue #60).

## Context

When `treasury` or `resolver` called `market-core` through the panicking
client methods generated by `contractimport!`, a `market-core` failure aborted
the whole invocation carrying **market-core's** numeric code. Because every
contract numbered its errors from `1`, the code a caller observed was
ambiguous: `Error(Contract, #7)` could mean `market-core::MarketNotFound` or
`treasury::DailyCapExceeded`, and the bindings' `Errors` maps (which decode by
number) happily mislabelled it. This caused wrong retries, alerts and user
messages.

## Decision

### Disjoint numeric ranges

Each contract owns a reserved range. Numeric codes are never reused across a
boundary, so `Error(Contract, #N)` identifies the emitting contract even before
you know which one it is:

| Contract            | Range          | Base constant           |
|---------------------|----------------|-------------------------|
| `market-core`       | `1..=999`      | (implicit)              |
| `resolver`          | `1001..=1999`  | `RESOLVER_ERROR_BASE`   |
| `treasury`          | `2001..=2999`  | `TREASURY_ERROR_BASE`   |
| `reasoning-registry`| `3001..=3999`  | `REGISTRY_ERROR_BASE`   |

`market-core` keeps its existing `1..=22` numbering: moving it would change
the ABI of an already-vendored wasm without a rebuild, and it is already
disjoint from every caller's range. The other three were renumbered in place
(variant names unchanged).

> Note: the `#[contracterror]` macro requires **integer-literal**
> discriminants (`soroban-sdk` rejects arbitrary expressions), so the enum
> variants carry literal values (`1001`, `1002`, …). The `*_ERROR_BASE`
> constants document and test the ranges; they are not used in the
> discriminants.

### No callee code escapes

Every cross-contract call in `treasury` and `resolver` uses the generated
`try_*` method and routes its result through one normalising helper:

```rust
fn core_call<T>(
    result: Result<Result<T, market_core::Error>, Result<soroban_sdk::Error, soroban_sdk::InvokeError>>,
) -> Result<T, Error> { ... }
```

- `Ok(Ok(v))` → `Ok(v)`.
- `Ok(Err(callee))` → mapped by `map_market_core_error` to a named
  `MarketCore*` variant (e.g. `MarketCoreMarketNotFound`), or
  `MarketCoreCallFailed` for the long tail.
- `Err(host)` → `MarketCoreCallFailed` (the invocation itself trapped or the
  callee was the wrong contract).

A mapping never swallows the error: it always returns `Err`, so the whole
invocation reverts and no partial state survives a failed cross-call. The
panicking generated methods are never used on the production path.

`treasury`'s name-dispatched trade calls (`core_trade`, which invoke
`buy`/`buy_v2` by symbol) cannot decode into `market_core::Error` without
exporting that type, so they map the numeric `soroban_sdk::Error` with
`map_market_core_code` using the same table.

### Host and auth failures

A missing `require_auth` or a host trap surfaces from `try_*` as
`Err(Err(InvokeError))` / a non-contract `soroban_sdk::Error`. These are not
callee contract errors and are **not** decoded by code; they collapse to the
single `MarketCoreCallFailed` / `RegistryCallFailed` variant. This is
deliberate: a revert discards events, so the original code is only recoverable
from simulation diagnostics, and the named variants cover every condition an
agent can actually act on.

### Append-only within a range

New variants take the next free number at the end of their contract's range.
Existing numbers are never reassigned; removing a variant leaves a documented
gap.

## Consequences

- Renumbering is a breaking change for anything that pattern-matches numeric
  codes. `docs/errors-migration.md` lists old → new per contract for the
  backend/frontend generated-error maps, and the four
  `packages/bindings/*/src/index.ts` `Errors` tables were updated.
- `treasury`'s constructor now fails with `panic_with_error!(&env,
  Error::InvalidConfig)` (a real contract error, code `2003`) instead of a
  string `panic!`.
- Guard tests in `treasury` and `resolver` enumerate both enums with `as u32`
  and assert the ranges are disjoint, so a future collision fails at test time.
- Mapping tests assert the exact caller-facing variant for each mapped failure.
- A fresh testnet deployment is required: the numeric codes are part of each
  contract's spec.
